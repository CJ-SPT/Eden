# Startup protocol and milestones

The startup configuration identifies release 24.01, codename `V24.01`, region `ccp`, and port 26000. The client's packaged MachoNet version module specifies **496**. The installed GPS transport and the build-matched Blue marshaller supplied the message order, field types, and serialization rules. [Blue marshal implementation](https://github.com/carbonengine/blue/blob/af0d65b29f951260ea09140ca11adf5d40566997/src/Marshal.cpp)

Each startup frame begins with a four-byte little-endian payload length. Blue marshal version 0 starts with `7e` and a four-byte shared-object count. The verified startup frames use zero shared objects. Eden accepts unflagged frames up to 16 KiB during this phase and reads each frame to completion before processing it. [Carbon transport flags](https://github.com/carbonengine/io/blob/8d8f339fd19f2e8095fcd90ad5415cb4ca00c331/src/protocol.h)

| Order | Sender | Payload |
| --- | --- | --- |
| 1 | Eden | Seven-field tuple containing marker 170472, protocol 496, pilot count 0, version 24.01 as a double, build 3662168, byte string `V24.01@ccp`, and update status `Unknown`. |
| 2 | Client | Six-field compatibility tuple with the same first six values. |
| 3 | Client | The tuple `(None, b'QC')` requests queue status. |
| 4 | Eden | Integer zero reports an empty login queue. |

The implementation compares the observed client messages byte for byte. A status request ends the probe. A login request continues into the encrypted account session. The host logs progress without recording arbitrary payloads.

## Encrypted local authentication

The development account uses the client's SSO launch path. After its version reply the client sends a VIP-key request and a pair of RSA-encrypted AES parameters. Eden acknowledges key negotiation, decrypts the local ticket with the session cipher, and validates its signature and expiry. Each side proves receipt of the other's random challenge before the server issues the account session. Two fresh client processes reported `LLV Succeeded` and sent the authenticated `machoNet.GetServiceInfo` call.

The client uses AES-256-CBC with per-packet padding. Challenge hashes cover a Blue-marshaled one-element tuple. The signed client expression is fixed to an empty dictionary. The outer MachoNet envelope may be zlib-compressed and contains another Blue stream for service arguments. The built-in string table comes from MIT-licensed Carbon Blue. [Carbon crypto](https://github.com/carbonengine/blue/blob/af0d65b29f951260ea09140ca11adf5d40566997/src/crypto.cpp) · [Carbon license](carbon-license.md)

## Shared flight ticks and celestial warp-ins, November 2, 2026

The server stamps both pilots' movement on the same one-second clock. A warp command sets the destination while the ship is still aligning. The pilot receives the warping effect immediately after the movement command. In build 3662168 the effect prepares the tunnel from the ball's destination. Its loop watches the native warp stamp before activating the camera and acceleration effects. Cancelling during alignment stops the effect. The client plays the arrival flash when it loads a remote ship already in warp.

Warp begins above 75% of hull speed with a velocity direction within the reference dot-product tolerance. A ship obstructed for 180 alignment ticks uses the reference timeout. SetState and AddBalls carry the ship's movement mode, velocity and speed fraction. An active warp also carries the original start stamp, distance, destination, minimum range and speed factor. On the first deceleration tick below the exit threshold the server carries the actual exit velocity into sublight motion. A legacy Stop tick damps vertical velocity before normal drag. Station approach recomputes thrust each tick, and sublight collision uses the first rigid surface crossed. [Destiny alignment](https://github.com/carbonengine/destiny/blob/27ee40b38a563d29054b32f64c3ebc87fabaec1f/src/Ball.cpp#L1898-L1920) · [Destiny simulation](https://github.com/carbonengine/destiny/blob/27ee40b38a563d29054b32f64c3ebc87fabaec1f/src/Ballpark.cpp) · [Destiny state stream](https://github.com/carbonengine/destiny/blob/27ee40b38a563d29054b32f64c3ebc87fabaec1f/src/Thunkers.cpp#L3246-L3302)

Warp-to-zero targets a celestial's nominal warp-in point. Planets use their ID, radius and position, large moons use their radius and position, and ordinary objects use the near edge. The requested range and ship lane offset apply relative to this point. With the installed catalog the nominal altitude is 30,342 km for Jita V and 5,164 km for Jita V – Moon 16. ## Native target locking, November 2, 2026

The pinned `eve/client/script/parklife/targetMgr.pyj` calls `dogmaIM.AddTarget(itemID)` and unpacks `(pending, targetList)`. The target service accepts visible ships and asteroid-category objects, validates surface range and available target slots including pending scans, and rejects self, unavailable objects and attempts outside a live non-warping ballpark. Asteroid spawning and mining activation remain separate work.

Lock duration in seconds is `40000 / (scanResolution * asinh(signatureRadius)^2)`, using a monotonic clock and the server's one-second session tick. Repeated AddTarget requests retain the original scan start. The pinned Ibis has 27,000 m base range, 475 scan resolution, signature radius 52 and three hull target slots. Long Range Targeting and Signature Analysis add five percent per trained level to range and resolution. The pilot's limit starts at two, adds Target Management and Advanced Target Management levels, and is capped by the hull. [CCP target-lock formula](https://developers.eveonline.com/docs/guides/useful-formulae/#target-lock-time). Attribute and skill IDs come from the build 3662168 catalog and are named in the corresponding enums.

A scoped handler owns pending scans and completed targets. A shared lock graph carries only ship IDs across connections; each connection emits its own `OnTarget("otheradd"/"otherlost", shipID, reason)` notifications. Range loss or a missing target cancels the scan or drops the lock. Beginning warp or a gate jump, docking, and disposing the connection remove outgoing and incoming locks. No locks are saved in the world database. Flight visibility and transit status reuse the existing Destiny implementation checked against [Carbon Destiny revision 27ee40b](https://github.com/carbonengine/destiny/blob/27ee40b38a563d29054b32f64c3ebc87fabaec1f/src/Thunkers.cpp). ## Civilian mining cycles, November 2, 2026

Build 3662168's `godma` calls `dogmaIM.Activate(moduleItemID, "miningLaser", targetID, repeat)` and `Deactivate(moduleItemID, "miningLaser")`. A scoped handler owns each running cycle and uses monotonic elapsed time, so duplicate activation cannot pay capacitor twice or restart its timer. Activation requires the pilot's fitted, assembled, online Civilian Miner, a completed asteroid lock, a non-warping ballpark and a target inside the module's surface range. The persistence layer separately validates ownership, the active ship, system, range and deposit. Activation currently supports Civilian Miners on corvettes; other mining modules and hull modifiers require further work.

The pinned Civilian Miner has range attribute 54 = 10,000 m, duration 73 = 10,000 ms, mining amount 77 = 6 m³ and capacitor need 6 = 5 GJ. Mining and Astrogeology each apply a separate yield multiplier of `1 + 0.05 * trainedLevel`. Whole ore units are rounded down. Critical chance 5967 starts at 0.01; critical bonus yield 5969 starts at 2. Mining Precision increases chance by ten percent per level and Mining Exploitation increases bonus yield by five percent per level. A full-cycle success adds the bonus to normal yield without removing that bonus from the asteroid. These values and skill ranks were checked in `client/typedogma` and its effect modifiers; [CCP's Catalyst notes](https://www.eveonline.com/news/view/catalyst-expansion-notes) confirm that critical bonus ore does not consume the deposit. This milestone rolls critical successes only for completed cycles. Manual deactivation returns whole units for the elapsed portion without a critical roll; this partial-cycle policy still needs comparison with the native server.

Each collection transaction reads the remaining deposit and free cargo space, clips extraction to both limits, adds to an owned ore stack or creates one, and subtracts only the extracted base units from the saved asteroid. Concurrent pilots serialize their writes to the same deposit. Capacity failure and invalid state cannot leave an ore-only or depletion-only write. Quantity-zero rows remain saved and disappear through the existing local `RemoveBall` path. Repeating cycles stop on full cargo, depletion, insufficient capacitor or lost target. Warp, docking, system departure and disconnect do not leave an offline mining job. A delayed tick completes one paid cycle and starts any next cycle at the current time rather than awarding unobserved catch-up cycles.

World version 16 adds `WorldShipEnergy(ShipId, Charge, UpdatedAt)`, initially empty for an existing save. A ship without an entry starts fully charged. Each paid activation saves charge and its UTC timestamp. Passive regeneration uses the pinned `godma.CreateChargedAttribute` and `GetChargeValue` curve: `capacity * (1 + (sqrt(charge/capacity) - 1) * exp(-5 * elapsedMilliseconds/rechargeMilliseconds))^2`. Capacitor Management adds five percent capacity per level; Capacitor Systems Operation reduces recharge time by five percent per level. Login snapshots include the regenerated charge. This milestone charges mining activation; warp capacitor consumption and capacitor warfare remain separate work.

The native HUD receives `OnGodmaShipEffect` and `OnModuleAttributeChanges`. Immutable mining contacts carry beam start/stop to other pilot connections through the existing Destiny updates, whose ballpark format follows [Carbon Destiny revision 27ee40b](https://github.com/carbonengine/destiny/blob/27ee40b38a563d29054b32f64c3ebc87fabaec1f/src/Thunkers.cpp). The server checks the active ship, current system and range again in a transaction before saving the destination station and removing the space position. The session releases location-bound references and refreshes station identity and launch coordinates. Reconnecting and undocking use the newly saved station.
