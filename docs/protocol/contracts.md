## Personal contract asset preparation

Implemented four previously unhandled preparation routes on `contractProxy`. Inert inspection of build **3662168** `contracts.pyj`, `createContractWnd.pyj` and `contractentry.pyj` confirms the calls `GetItemsInDockableLocation(stationID, forCorp)`, `GetItemsInContainer(stationID, itemID, forCorp, flag)`, `GetNumItemsInContainers(stationID, itemIDs, forCorp, flag)` and `SplitStack(stationID, itemID, quantity, forCorp, flag)`. The creation window consumes standard inventory rows, including virtual `singleton` and `stacksize`; container counts are an **integer-keyed dictionary**, and a truthy split reply triggers `OnItemSplit` and refresh. The handler uses the existing nine-column inventory DBRow adapter and returns Boolean True after a committed split. No codec change is needed.

Station reads contain owned personal hangar items and inactive assembled hulls. They exclude installed manufacturing blueprints, active ships, hulls in space and carried hulls. A selected pilot may inspect or split a remote personal station hangar, including from space. Container previews validate the root against the same station selection and traverse owned nested contents, retaining original item IDs, location IDs and flags. This includes fitted modules, loaded charges and carried ships; the count measures rows rather than summed stack quantities. Ordinary packaged items have zero contents. Reads use a world transaction so root validation and nested traversal see one snapshot. Foreign, missing and non-root selections fail rather than exposing another inventory. Corporation asset requests and non-personal-hangar flags are explicitly rejected.

`ContractAssetRules` owns the pinned `contractscommon.MAX_NUM_ITEMS` selection limit of **500**, distinct positive IDs and two-positive-part packaged-stack rules. Splitting requires an owned, available, offline, non-singleton stack directly in the specified hangar. It rejects installed items and items with nested contents, preserves per-stack damage metadata, allocates a durable inventory identity and commits the quantity reduction and separate new stack together. It deliberately does not merge the separated portion. Native `OnItemChange` notifications carry the original quantity for the old stack and an entering-container change for the new stack; blueprint splits invalidate the blueprint cache once. Existing world version **49** and inventory tables suffice; no schema migration or runtime database edit is needed.

This was the preparation milestone only. Its then-pending item-exchange lifecycle and compatibility replies are implemented in the following milestone, followed by courier and auction contracts below.
