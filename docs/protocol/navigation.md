## Station-origin TR camera sequencing, November 8, 2026

The maintainer reports that TR from a station into sovereignty nullsec leaves the camera unresponsive. Offline inspection of pinned build **3662168** shows a sequencing race in the source-space bootstrap: Eden's first source `SetState` immediately queued `effects.JumpDriveOut` in the same Destiny update. `michelle.Park.SetState` sends `DoBallClear`, and `GameUI.DoBallClear` starts the asynchronous `_DoBallClear` task. That task finalizes any active space-to-space transition. Meanwhile `JumpTransitionTunnel.Prepare` selects `CAM_JUMP`, and `InflightLayer.OnActiveCameraChanged` assigns no mouse camera controller to that cinematic camera. A source scene reset can therefore overlap the newly started jump transition. Additional source `UpdateStateRequest` replies during departure could also finalize it before destination arrival. This is a protocol-order finding; no client exception trace or live camera recovery was captured.

Queued station/unbound-source translocations now publish the source full state separately. Only after its Destiny notification has been successfully sent may a later Destiny tick start the departure effect and its existing three-tick transfer interval. Failed writes cannot start that interval. Source full-state retries are suppressed after publication and during departure, while the destination still receives its own full state and one jump-drive arrival effect. The ready, already-bound space-origin path retains its immediate departure. Disconnect cancels pending travel and retains the actual source undock position. No database schema, client files, saved camera preferences or sovereignty state change.

## Developer translocation

The pinned client's **GM / WM Extras → TR me here!** menu calls `menuSvcExtras.devFunctions.SlashCmdTr`, which sends `slash.SlashCmd('/tr me ' + itemID)` and then clears local align targets. Eden now owns this selected-pilot route through `TranslocationHandler`. Authorization uses the authenticated account's `ROLE_GML | ROLE_WORLDMOD` bits, matching the native menu; launcher developer accounts contain both. Ordinary player/QA-only roles, another subject, arbitrary coordinates, additional flags, unsupported slash commands, malformed IDs and unexpected keywords reject without cancelling navigation or moving inventory. Native `machoVersion` metadata is stripped by the router. This milestone implements the menu's command, not the general developer-console command registry.

`IPilotTranslocation` and typed target/result records live in Gameplay. The server resolves known solar systems, NPC stations and normalized catalog celestials, including standard gates, planets, moons and stars. Solar-system destinations use their star when available, otherwise the system origin; space arrivals start 10 km beyond the target's surface plus the ship radius and move clear of overlapping catalog bodies. NPC station targets dock the same active hull directly. Runtime targets such as another pilot, player structures and client-only secondary suns/disrupted gates are outside this initial target resolver. The radius/clearance policy is Eden's developer-travel policy, not a claim about stock server GM placement.

The SQLite operation validates the expected active hull and ownership, then updates its station/position and projects the inventory change in one transaction. Cargo, ammunition, fitted items, other hulls, clone/home state and wallet are retained. Destination initialization occurs before acquiring the move transaction because loading a system may initialize its asteroid rows through a separate writer. Failed position/ship writes roll back the move. The teleport itself does not award ordinary undock/jump task events or charge a fee; an automatic source undock uses the existing undock tracking once. Existing activity shutdown runs before a valid move, preserving paid costs/cooldowns and stopping further automatic cycles. Flight relocation clears old motion/history, warp/gate orders and location bindings. Same-system observers receive absolute position/zero-velocity/Stop commands; the owner receives a fresh full state. Cross-system observers remove the departed hull and add it after destination binding.
