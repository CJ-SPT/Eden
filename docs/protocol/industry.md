## Currency redemption and loyalty wallets

Pinned `inventorycommon.const` identifies **52996** as `typeKredits` and **73277** as `typeLoyaltyPointsHeraldry`; the catalog names them **InterStellar Kredits (ISK)** and **EverMarks**. Both have zero volume and portion size one. ISK is in Money group **17**, category **4**, so the earlier broad material-delivery rule incorrectly allowed it to become an ordinary packaged item. Claims now classify these two currency types before inventory delivery. Quantity credits **one ISK** (100 saved cents) or **one EverMark** per unit, creates no inventory, and consumes the pending token atomically. Fixed-station issuance rejects these automatic rewards. They work in space and before selection, including alongside SP rewards; ordinary inventory failures retain their normal per-token errors. Expiry, authenticated-account/recipient checks and replay protection apply unchanged.

`LoyaltyWalletHandler` replaces the empty `LPSvc.GetAllMyCharacterWalletLPBalances()` compatibility reply. It requires a selected pilot, exactly zero arguments and no additional keywords. The native reply is a **list of `(issuerCorporationID, points)` tuples**, ordered by issuer, with positive balances only. The pinned `loyaltyPointsWalletSvc` reads `row[0]` and `row[1]`, separates Paragon **1000419** using `appConst.corpHeraldry`, and uses that issuer for the dedicated EverMarks balance. Saved LP balances are private to the selected pilot; a caller cannot supply another owner. Unknown/corrupt persistence rejects rather than inventing balances. EverMarks' association with Paragon is also described by [CCP's EverMarks guidance](https://support.eveonline.com/hc/en-us/articles/14178451504796-Evermarks).

The selected recipient receives one cash `OnAccountChange` with the final balance and one native **`OnLPChange(None, issuerCorporationID, before, after)`** for an EverMarks batch, followed by the existing queue refresh. Native inventory updates are absent for currency. Archive-wide inert inspection found one `OnLPChange` consumer: it ignores the first change-type argument, clears its character LP cache and emits the local balance event using the other three values. The adapter deliberately uses None for that unused parameter. A selected session polls its own LP snapshot once per second, detects a separate writer, reports decreases/removal to zero, and suppresses unchanged repeats. A separate cash-balance monitor also reaches external cash credits; it suppresses a duplicate when market/combat/contracts or redemption already queued the same committed balance. Before selection or for a different owned recipient, only persisted funds and the account queue change; that pilot's next selection reads its own balances.

ISK credits use the pinned catalog/accounting type **147**, **Redeemed ISK token**, with name message **552388**, in the existing personal wallet journal. Each token retains a receipt and its exact resulting cent balance. The Eden journal namespace is **13,000,000,000,000 + tokenID**; the administrator-issued source uses the existing SCC issuer policy and the token ID as the reference. Equal-time cash entries retain newest-token-first order. Normal last-30-day/month filters apply; balances and receipts survive restart. EverMarks receipts stay in currency accounting and are not fabricated as ISK journal entries.

World version **57** adds `WorldLoyaltyWallet` keyed by pilot and issuer, and `WorldRedeemedCurrency` keyed by consumed token with pilot/time indexing. Pilot/account token ownership remains enforced through the existing foreign keys and claim transaction. Currency quantities and balance arithmetic use typed checked rules, preserving the prior state on overflow. Receipt/token failures roll back cash, LP, SP, inventory and every consumed token in a mixed batch. Competing claims can credit a token once. A genuine version-56 migration retains SP and existing assets while initializing the new tables. It does not automatically credit old erroneous ISK stacks: an intact historically redeemed ISK stack can use the existing ownership/location/provenance-checked reversal, then its replacement token credits cash once; removal precedes that credit and replay cannot duplicate it. No installed runtime save was changed by agent validation.

## Mining-laser fitting, November 2, 2026

World version 14 adds `Singleton` and `Online` to owned items, defaulting existing cargo and hangar stacks to false without repeating the grant. A docked pilot can fit one mining laser from each selected stack into the active ship's high slots. Fitting checks ownership, source location, the hull's high-slot and turret counts, and all six required-skill attribute pairs from the catalog. A split preserves the remainder and creates one assembled module in the same transaction. Unfitting moves that module to the station hangar or cargo, clears its online state, and checks cargo capacity when applicable. Other module families remain unavailable until their passive modifiers are implemented.

The pinned `inventorycommon.const` defines high slots 27 through 34, cargo 5, hangar 4, auto-fit 0, stack-size column 9 and singleton column 10. An assembled module has quantity -1, stack size 1 and singleton 1 on the wire. Catalog mining-laser group 54 includes Civilian Miner 3651, requiring Mining I and consuming 65 CPU and 2 power grid when online. CPU Management 3426 and Power Grid Management 3413 add five percent output per trained level. Eden validates those resource totals before `dogmaIM.SetModuleOnline(shipID, moduleID)` and persists online state; `TakeModuleOffline` releases the load. The new code groups these flags, attributes, effects, skills and service values in named enums and constants.

The station's circled ship icon calls the bound `corpStationMgr.DoStandingCheckForStationService(17)` before opening Fitting. Bindings require the current docked station and expire on departure. The fitting managers return empty saved/community fitting dictionaries; template writes remain unsupported. The pinned `godma`, `clientDogmaLocation`, fitting-window and inventory scripts supply these method signatures and field shapes. `UnloadAmmo` succeeds without changes for supported mining lasers, which have no charges.

`GetAllInfo` includes fitted modules in `shipInfo` and the instance cache. `ItemGetInfo` returns the owned module's inventory row, catalog attributes, online attribute and online effect. Inventory changes use `OnItemChange`; online toggles use `OnGodmaShipEffect`, followed by `OnModuleAttributeChanges` for ship CPU, power and turret availability. An early live refresh sent `OnGodmaPrimeItem`, whose godma row differs from the native inventory descriptor and caused `clientDogmaLocation.IsFitted` to remove the module. The corrected path lets the normal item change fetch module info and updates attributes/effects without replacing that row. Blue reductions reuse the existing codec checked against [Carbon Blue revision af0d65b](https://github.com/carbonengine/blue/blob/af0d65b29f951260ea09140ca11adf5d40566997/src/Marshal.cpp).

## Persistent asteroid fields, November 2, 2026

The pinned catalog's `client/asteroidcountbytypeidbeltid` supplies ore type/count pairs for each belt anchor. Perimeter has three belts containing 93, 123 and 135 rocks (351 total); Jita has none. The fields contain Veldspar, Scordite and their grade variants. `client/types` supplies ore volume. These exports do not supply individual rock IDs, positions or remaining quantities. Eden generates those once per belt and saves them in world version 15. Its local field policy uses a 6–18 km ring with 4 km thickness, 5,000–15,000 m³ deposits, radius proportional to the square root of initial deposit volume, and stable IDs above the 32-bit range. These dimensions and deposits are Eden policy, not asserted stock-server values. Migration preserves pilot and inventory data. Quantity-zero rows remain saved and are omitted from the visible field, preventing regeneration after depletion or restart; no mining operation reduces those quantities yet.

Asteroids use Destiny rigid mode 11 and the massive flag, with local rather than global coordinates. Catalog celestial markers keep their global flag. Both reconnect snapshots and streamed `AddBalls` carry the raw ball bytes, slim items and damage dictionary; `RemoveBall` unloads rocks outside Eden's 250 km visibility range. Streaming does not reset the rest of the ballpark. The coordinate and serialization behavior was checked against [Carbon Destiny Ball.cpp, revision 27ee40b](https://github.com/carbonengine/destiny/blob/27ee40b38a563d29054b32f64c3ebc87fabaec1f/src/Ball.cpp), with the existing AddBalls path checked against Thunkers.cpp at the same revision. The pinned `asteroid.pyj` selects graphics and rotation from type, radius and item ID; `asteroidBelt.pyj` supplies the belt marker's ambient effects. Asteroid types lack an explicit signature-radius attribute, so targeting uses dogma attribute 552's catalog default of 100.

The first full-field arrival exposed an unrelated transport limit: encrypted gameplay packets still inherited the 16 KiB startup bound. Sending the field exceeded that bound and disconnected the session. Gameplay frames and decompressed packets now have a separate 1 MiB Eden limit; the startup exchange retains 16 KiB, and unsupported high header flags remain rejected before allocation. The pinned `SocketGPS.pyj` delegates frame I/O to native `recvpacketoob`/`sendpacket`, and `machoNetTransport.pyj` accepts Blue data with optional zlib compression. The larger bound is a local resource limit, not a claim about the native server's maximum. No transport flags or encryption format changed.

## Civilian mining cycles, November 2, 2026

Build 3662168's `godma` calls `dogmaIM.Activate(moduleItemID, "miningLaser", targetID, repeat)` and `Deactivate(moduleItemID, "miningLaser")`. A scoped handler owns each running cycle and uses monotonic elapsed time, so duplicate activation cannot pay capacitor twice or restart its timer. Activation requires the pilot's fitted, assembled, online Civilian Miner, a completed asteroid lock, a non-warping ballpark and a target inside the module's surface range. The persistence layer separately validates ownership, the active ship, system, range and deposit. Activation currently supports Civilian Miners on corvettes; other mining modules and hull modifiers require further work.

The pinned Civilian Miner has range attribute 54 = 10,000 m, duration 73 = 10,000 ms, mining amount 77 = 6 m³ and capacitor need 6 = 5 GJ. Mining and Astrogeology each apply a separate yield multiplier of `1 + 0.05 * trainedLevel`. Whole ore units are rounded down. Critical chance 5967 starts at 0.01; critical bonus yield 5969 starts at 2. Mining Precision increases chance by ten percent per level and Mining Exploitation increases bonus yield by five percent per level. A full-cycle success adds the bonus to normal yield without removing that bonus from the asteroid. These values and skill ranks were checked in `client/typedogma` and its effect modifiers; [CCP's Catalyst notes](https://www.eveonline.com/news/view/catalyst-expansion-notes) confirm that critical bonus ore does not consume the deposit. This milestone rolls critical successes only for completed cycles. Manual deactivation returns whole units for the elapsed portion without a critical roll; this partial-cycle policy still needs comparison with the native server.

Each collection transaction reads the remaining deposit and free cargo space, clips extraction to both limits, adds to an owned ore stack or creates one, and subtracts only the extracted base units from the saved asteroid. Concurrent pilots serialize their writes to the same deposit. Capacity failure and invalid state cannot leave an ore-only or depletion-only write. Quantity-zero rows remain saved and disappear through the existing local `RemoveBall` path. Repeating cycles stop on full cargo, depletion, insufficient capacitor or lost target. Warp, docking, system departure and disconnect do not leave an offline mining job. A delayed tick completes one paid cycle and starts any next cycle at the current time rather than awarding unobserved catch-up cycles.

World version 16 adds `WorldShipEnergy(ShipId, Charge, UpdatedAt)`, initially empty for an existing save. A ship without an entry starts fully charged. Each paid activation saves charge and its UTC timestamp. Passive regeneration uses the pinned `godma.CreateChargedAttribute` and `GetChargeValue` curve: `capacity * (1 + (sqrt(charge/capacity) - 1) * exp(-5 * elapsedMilliseconds/rechargeMilliseconds))^2`. Capacitor Management adds five percent capacity per level; Capacitor Systems Operation reduces recharge time by five percent per level. Login snapshots include the regenerated charge. This milestone charges mining activation; warp capacitor consumption and capacitor warfare remain separate work.

The native HUD receives `OnGodmaShipEffect` and `OnModuleAttributeChanges`. A live check found that the godma state manager accepts an optional trailing `stall`, while `PlayerShip.OnGodmaShipEffect` accepts only eleven external arguments; notifications now use their common eleven-argument shape. `clientDogmaLocation.OnModuleAttributeChanges` unpacks eight fields per change, including wallclock time, so both capacitor and fitting-resource notifications now include that eighth value. Module info snapshots preserve a running mining effect. The client receives `OnSpecialFX` with the module ID/type, asteroid ID and `effects.Laser`; fitted module triples in ship slim items let observers fit the correct turrets. Immutable mining contacts carry beam start/stop to other pilot connections through the existing Destiny updates, whose ballpark format follows [Carbon Destiny revision 27ee40b](https://github.com/carbonengine/destiny/blob/27ee40b38a563d29054b32f64c3ebc87fabaec1f/src/Thunkers.cpp). Effect method signatures and turret selection come from the pinned Python client.

Returning from the belt exposed the earlier restriction that `CmdDock` accepted only the ship's saved departure station. Docking now accepts a catalog station in the current system within 2,500 m of the station/ship surfaces. The server checks the active ship, current system and range again in a transaction before saving the destination station and removing the space position. The session releases location-bound references and refreshes station identity and launch coordinates. Reconnecting and undocking use the newly saved station. This supports unloading locally after a gate trip instead of requiring a return to the original station.

`OnOreMined` supplies the dictionary expected by `oreMinedNotificationAdapter`: `oreType`, `quantity_added`, `quantity_removed`, `hasRewards`, `amountWasted`, `amountCritBonus`, `itemID` and `moduleItemID`. It drives the native mining message and mining signals. The inventory notification reuses the Carbon Blue DBRow codec. A new stack must include old location/flag zero in `OnItemChange`: quantity-only changes updated the cargo meter but did not insert the unknown stack into the container cache. Existing stacks retain their previous quantity. The same corrected insertion path applies to split cargo stacks and newly assembled fitting items.

## Station ore reprocessing

Build 3662168's `reprocessing/ui/quotes.pyj`, `inputItemAdder.pyj`, `itemReprocessor.pyj`, `controller.pyj`, `reprocessingWnd.pyj` and `reprocessing/util.pyj` define this exchange. `eveMoniker.GetReprocessingManagerEx` binds `reprocessingSvc` to the station ID. `appConst.stationServiceReprocessingPlant` is service **5**, checked through `corpStationMgr.DoStandingCheckForStationService`. Eden validates the current docked station and its catalog operation's service list, and releases the reprocessing binding on location changes.

`GetQuotes(itemsByID, activeShipID)` receives a dictionary of item IDs to packed inventory rows, rather than a list of IDs in the native window. Eden reads those rows as inert data and uses only the dictionary keys; quantities, types, ownership and locations come from SQLite. The reply is `(stationTax, stationEfficiencyByType, quotesByItemID)`. The efficiency dictionary needs a genuine Python `None` key for its default. Quote KeyVals contain item/type IDs, `quantityToProcess`, `leftOvers`, `portions`, `efficiency`, `recoverables` and `totalISKCost`. Each recoverable exposes `typeID`, `client`, `unrecoverable` and `iskCost`.

Blue decoding now recognizes allowlisted `blue.DBRowDescriptor` reductions and the packed DBRow token. Descriptors specify numeric data length, null/bool bits and separately marshaled object columns. The reader validates the packed zero/literal runs and preserves the data without executing Python globals. Dictionary encoding retains Carbon's value-before-key order, including `None` keys. Wire behavior was checked against [Carbon Blue revision af0d65b, PyRowSet.cpp](https://github.com/carbonengine/blue/blob/af0d65b29f951260ea09140ca11adf5d40566997/src/PyRowSet.cpp) and [Marshal.cpp](https://github.com/carbonengine/blue/blob/af0d65b29f951260ea09140ca11adf5d40566997/src/Marshal.cpp).

Recipes come from `client/typematerials`; batch size and volume come from `client/types`. The station's `sde/npcStations` record supplies base efficiency and station take. For ores, efficiency is the station value multiplied by the trained Reprocessing, Reprocessing Efficiency and ore-specific skill factors, capped at one. Dogma attribute 379 supplies each skill's percentage per level; ore attribute 790 identifies its specialized skill. Each output is floored after multiplying its catalog quantity by complete portions and efficiency. Leftovers stay in the source stack. At station 60003754, base efficiency is 0.5 and station take is 0.05; one 100-unit Scordite batch has base materials 150 Tritanium and 110 Pyerite, yielding 75 and 55 without reprocessing skills.

The pinned build charges station take in **ISK**, using adjusted average material prices; it does not subtract station tax from mineral quantities. Its fixed-material helper substitutes zero when a price is missing. Eden's existing average-price response is empty, so this milestone reports zero ISK costs and does not debit the prototype wallet. Market pricing, wallet transactions, standing discounts, implants, structure rigs, equipment recycling and randomized output recipes remain separate work. Fixed ore recipes and personal cargo/hangars are the supported scope.

`Reprocess(itemIDs, fromLocation, ownerID, outputLocationID, outputFlagID)` recalculates the quote in a SQLite transaction. It validates the docked station, ownership, active ship, source and output containers, distinct IDs, complete batches, output integer limits and cargo capacity after consuming input. The transaction consumes ore, retains remainders, merges or creates mineral stacks and saves everything together. A stale or repeated request cannot reprocess an incomplete remainder or missing stack. The reply is the processed-ID list paired with actual output quantities by type; the native controller uses this to display its results panel. Inventory changes update ore quantity and insert new mineral stacks through the existing three-argument `OnItemChange`. No world-schema migration or starter grant is needed.
